# Data Model: Reliable Worker Recovery

Design proposal only; these records do not yet exist in code. SQLite is the proposed local core ledger, pending human plan-gate decision; the approved specification remains WHAT. Q1/Q2/Q3 retain their recorded human answers; the supervision, receipt protocol and checkpoint fingerprints are proposals. Human-proposed 10s overall/2s per-call values remain unmeasured, non-SLO defaults. Deadline/cache response, contained invocation accounting, secondary cleanup, quarantine and unsupported-host rules follow the contract: every admitted supported status operation returns by configured D independently of child reap. Catastrophic caller-process/OS unavailability is outside operating preconditions, not a successful response. Persisted state is authoritative, never conversation/session history. Validate typed/versioned records at boundaries; bound fields/sizes; use UTC-aware timestamps and safe errors.

## Records

### TaskOwnership
`task_id` (opaque bounded identifier) is scoped by the composite `task_key=(project_key, feature_dir_key, stage_key, unit_key)`; `project_key` is opaque and provisioned for the receiving project, while `feature_dir_key` is relative to that project root. Include the applicable lifecycle/plan/unit checkpoint revision or fingerprint, `ownership_revision` (monotonic; rollback rejected), `evidence_revision` (monotonic), `generation` (monotonic core-write fence), nullable `owner_host`/`execution_id`, `scope_ref` (safe reference/digest), `updated_at` (UTC), and `integrity_state` (`valid|unknown|corrupt`). The composite task key, not `task_id` alone, is authoritative and is a unique composite key in the proposed schema. Transactional compare-and-update is serialized by the one project-root ledger across features, only for cooperating core writers; this is not host exclusion.

### WorkerIdentity
Host-issued stable `host_id`, the composite `task_key` (with `task_id` only as an opaque alias), unique `execution_id`, authorized `generation`, `issued_at`. Missing, spoofed, mismatched or ambiguous identity/key binding => unknown/blocked; do not guess.

### StatusObservation
`outcome`: exactly `running|delayed|unavailable|unknown`; task/source IDs, `observed_at` (UTC), source/evidence/ownership revisions, last-known owner and progress reference, evidence status (`verified|incomplete|inaccessible|ambiguous|conflicting|stale|none`), `evidence_age_ms` (nullable if unknown), `evidence_source`, bounded `uncertainty`/limitations and `safe_next_options`, optional last-decisive observation time. Heartbeat/list presence/absence are advisory, never death proof. Include `response_origin=current|cache|empty_cache`, invocation reference if any, `deadline_outcome=completed_before_deadline|cached_by_deadline`, `cleanup_outcome=not_started|pending|complete|unknown`, `quarantine_active`, and cached guard state/revision (explicitly unknown if stale). No invented age/source for empty cache; label absence/uncertainty. A timeout produces unavailable/unknown, not stopped; cached owner/progress is last-known, not current liveness or transfer permission. Safe options include inspect cached evidence, await reconciliation or seek human review; none bypass guards.

### StatusCacheSnapshot / StatusRequestBudget (PROPOSED)
Bounded immutable, safe-to-return snapshot per task, preloaded before admission by a separate publisher; initialize absent/corrupt/inaccessible evidence to explicit empty/unknown. Include observation above, snapshot/source revisions, UTC observation/publication times and runtime monotonic age anchor where available. Nonblocking atomic snapshot publication/read, no foreground ledger/cache-writer lock, fresh DB query or payload load. A snapshot is an observation, never ownership authority. Stale guard/source revisions remain labeled unknown and cannot authorize mutations. Cache reads continue during quarantine without invoking an adapter.

Runtime-only budget: request start before admission; positive finite configured wait, `D`, platform-verified fixed rendering/handoff reserve `R`, `response_cutoff=D-R`, prevalidated minimum useful guard/creation/work duration, bounded response size and reserved output channel, configured adapter cap and per-call end. Prevalidate a fixed bounded template and nonblocking enqueue/caller return. Reject configuration/request before status waiting if the configured deadline or actual remaining time at admission cannot accommodate the verified reserve or output capacity cannot be assured; no status request was admitted or claimed to meet D. R=250ms is a proposal only, not a presumed bound; inability to prove the selected reserve makes the platform unsupported. If D-R is nonpositive, D-R <= t, or time before D-R is less than the minimum useful budget, do not create an invocation guard or spawn; immediately return the prebuilt cache as unavailable/unknown by D. Late guard persistence after an initially sufficient budget instead requires no spawn and reconciliation of any unresolved guard. If the bounded immutable snapshot is absent or invalid, use an explicit fixed bounded empty/unknown response prepared before request; do no DB or logging work during handoff. Foreground returns a validated current result or that cache by D for every admitted supported status operation independently of adapter behavior, child exit/reap and cleanup. Adapter invocations are never inline and run only in validated isolated contained children; known blocked, uncontained or non-cooperative adapters and unsupported Windows are rejected before status admission and before any call/spawn. Catastrophic caller-process/OS loss/freeze is outside ordinary operating preconditions, not an adapter exception.


### CheckpointRecord / CheckpointEvidence
Checkpoint: opaque ID/task, recorded progression sequence, scope, criteria IDs/descriptions, completion claim per criterion, evidence references/digests per criterion, verification identity/command+environment reference/result/evidence, relevant-state fingerprint, created time/revision and eligibility (`candidate|verified|invalidated|unknown`).

Eligibility requires FR-007/008: identifiable scope, criteria, claim and applicable verification/result; accessible/interpretable evidence sufficient for each; current relevant state matches; and unambiguous order. Only latest eligible checkpoint is resumable. One planned specification-conforming fingerprint design binds canonical relevant inputs, transitive dependencies, instructions, command/environment identity and verification evidence; the human did not select exact fingerprint details. Relevant changes invalidate dependent claims only; unrelated progress stays. Missing/inaccessible/contradictory/insufficient evidence, ambiguous ordering or changed state is not verified/resumable. Exact fingerprint serialization/hash/filesystem identity remains an implementation choice subject to review.

### RecoveryProposal / AuthorizationContext / HumanDecision
Proposal: ID, task, action (`continue|transfer`), bounded scope, observed revision/generation, checkpoint/evidence digests, safety evaluation/reason codes, allowed and excluded actions. Explicitly exclude money movement and customer-record changes.

`AuthorizationContext`: receiving-project-authenticated principal and tenant; exact action/task/scope; decision nonce; evidence and evidence revision; expected owner generation/revision; expiry/currentness data and opaque provenance reference. The receiving host verifies authorization, expiry and currentness at fence time. Missing identity, tenant mismatch, stale/replayed nonce/decision, or any mismatch blocks. Persist only opaque provenance references; actor strings are not credentials.

Decision: ID/proposal, (`approve|reject`), bound `AuthorizationContext`, authorized scope, evidence revision, ownership generation, UTC decision time, review status (`presented|reviewed` only if substantiated), result (`accepted|rejected|stale|blocked`). Accept only if scope/revision/generation/provenance still match; reject stale/replay. Approval cannot waive exclusion or evidence; human approval is not host exclusion.

### RecoveryTransfer
`transfer_id` unique within the composite task key, stable task reference, prior execution, tenant reference, expected owner generation/revision, proposed new generation, exact decision/scope/evidence revision digests, `decision_digest`, SQLite status (`TRANSFER_PENDING|COMMITTED|BLOCKED`), idempotency key equal to transfer ID, and opaque durable host receipt reference/digest persisted with the final commit. A host may already be durably fenced while the SQLite row remains `TRANSFER_PENDING`; reconciliation uses the same ID. SQLite first records `TRANSFER_PENDING` in a transaction using expected generation/revision. The host durably fences prior task+execution+generation before any new execution is permitted and returns a receipt bound to feature/task, tenant, previous/new generation, execution, exact decision/scope/evidence revision and transfer ID. SQLite persists receipt and final generation with ownership/transition history/recovery_audit in a second transaction. New generation cannot launch until receipt and DB final commit both exist. A crash after host fence but before final DB commit leaves old fenced/new unlaunched; recovery queries/replays the same ID and never reopens old. If receipt/fence persistence across restart is not guaranteed, block. This is not a cross-system atomic transaction.

### HostCapabilitySnapshot
Host/adapter/launcher version, OS, evidence reference and capability assessment; states include `controllable_child_creation` and `tree_termination_confirmed` (`confirmed|unsupported|unknown`), stable identity, bounded observation, durable records, atomic generation fence, durable exclusion/receipt/query-or-idempotent-reconciliation across restart, bounded creation/IPC/termination/wait/reap/resource cleanup, parent-owned killable process-tree containment before adapter code executes, parent-loss/shutdown fail-closed behavior, service-side idempotency/operation deadline, responsive foreground/bounded output-handoff evidence, preloaded-cache/nonblocking publication evidence, proposed inline cleanup-effort cap and response reserve; limitations. A trusted preflight must verify these without executing an unqualified adapter child; a declaration is not proof. Per-invocation cancellation, termination, wait/reap and no-child evidence are required before guard release. False, unsupported, unknown, timed-out, stale or inconsistent capability => unsupported and no adapter execution/new work. No uncontained fallback, helper thread or multiprocessing substitute.

Windows adapter execution and supervision are unconditionally unsupported and out of scope for this increment, irrespective of snapshot values: fail closed before any adapter call/worker spawn/status timeout/transfer. Windows authoring/review and pure model/contract tests without adapter execution or spawn remain possible. The current supported-host set is empty, with all actual transfers blocked everywhere; this generic model qualifies no platform. Windows support requires a separate scoped design/feature and independent platform security review of broker or outer containment, CreateProcess/Job attachment and parent-loss races; it is not a deliverable here. Known inability to sustain responsive foreground supervision rejects platform admission before execution. Adapter/ledger/sink hangs and delayed reap cannot delay the supported status return by D. Catastrophic caller-process/OS loss/freeze is outside operating preconditions, not deadline satisfaction. 10s/2s and 500ms inline cleanup cap/250ms response reserve remain unmeasured, non-SLO proposed defaults.

### AdapterInvocation / AdapterTaskGuard (PROPOSED)
Parent-owned records, scoped by composite `task_key` and opaque `adapter_id`. `AdapterInvocation` has unique `invocation_id`, operation kind (`read|fence|receipt_query`), optional durable `transfer_id` (mandatory for fence), supervisor instance, child identity (PID plus creation/instance token; PID alone is reusable), creation state (`not_started|pending|suspended|contained|resumed|canceled|unknown`), opaque host containment identity, runtime parent-owned containment handles (never serialized as reusable authority), containment-before-execution evidence, pending-creation cancellation outcome, tree termination/wait/reap/no-child evidence references, parent-loss/shutdown outcome, runtime monotonic request start/overall deadline/response cutoff/call end/optional earlier work cutoff, inline cleanup-effort cap (not a required reserve), response reserve, foreground response completion/origin (runtime observation, not a required synchronous DB write), UTC diagnostic times, tree state (`active|termination_confirmed_reaped_no_child|death_unconfirmed`), cleanup state (`pending|complete|unknown`), bounded reason and evidence references. Monotonic values are runtime-only and never reused as deadlines after restart. No credentials, adapter payloads or raw exceptions are stored.

`AdapterTaskGuard` has `state=idle|active|quarantined|reconciling`, guard revision, active invocation ID, optional transfer ID and bounded quarantine/reconciliation reason/evidence. Proposed SQLite tables `adapter_invocation` (composite task key + adapter ID + invocation ID primary key) and `adapter_task_guard` (composite task key + adapter ID primary key) reference the same scoped task ownership row. Admission atomically checks every unresolved guard for the composite task key, including other adapters/supervisors, and claims the guard before creation; only parent records cleanup. Status-request admission is separate from adapter-invocation admission: cache-only status bypasses no guard and launches no child. At most one active invocation for that task; unresolved guards block any same-task adapter invocation/retry, ownership mutation and new execution, including through another adapter. Each ownership/launch transaction checks those guards atomically under ledger serialization; only associated finalization/reconciliation may advance after confirmed cleanup and verified remote outcome. Persist active intent before spawn, so failed quarantine persistence still leaves a durable block. Unknown DB write/cleanup result blocks rather than assuming idle. On parent termination/host shutdown, native containment must fail closed (including pending/late creation), not rely on a guard to kill processes. On restart, active/pending/quarantined guards remain blocked until authoritative creation/tree-cleanup and remote-outcome reconciliation, never automatically expire by timestamp. If this behavior cannot be enforced/confirmed, the adapter/platform is unsupported.

Transitions: `idle -> active` before spawn; `active -> idle` only after pending/late creation cancellation/resolution, confirmed contained-tree termination/wait/reap with no child remaining and resource cleanup and no unresolved mutation outcome. Spawn uncertainty or unconfirmed death/cleanup => `quarantined` (the durable active guard remains the block if a later quarantine write cannot complete); ambiguous fence outcome remains guarded even after child death. No same-task adapter call/retry/new work, including through another adapter, until all pending/late creation is resolved and the contained tree is confirmed terminated/reaped with no child remaining. Quarantine is only a durable admission block, not containment. A still-contained status child may continue temporarily after the foreground returns by D; persistent killable containment and secondary cleanup remain active. Cleanup is required before guard release, never before cache-only status return. Never clear a guard solely on worker PID exit or elapsed time. `quarantined -> reconciling` requires that complete creation/tree-cleanup confirmation and explicit reconciliation admission, not ordinary retry/new execution; allow only necessary read/query of the same transfer ID under the same budgets. Keep mutations/launch blocked until local cleanup and remote/receipt reconciliation are complete and durably recorded. Same-ID replay elsewhere means reconciliation under the adapter contract, never blind retry. Old fence is never reopened; local kill cannot cancel remote effects. Failed/absent reconciliation leaves the guard quarantined.

### SideEffectOutcome
Opaque effect/task reference, status `not_started|confirmed|unknown`, evidence reference/revision. Unknown forbids replay; no exactly-once guarantee.

## Proposed SQLite schema, transactions and crash consistency

This is an implementable storage proposal, not an approved deployed backend. Proposed future path: the receiving project root `.specify/recovery/recovery.sqlite3`, shared by that project's features and created only by future implementation. This plan-stage correction does not create the database or `.specify/recovery/`. There is exactly one ledger per receiving-project root; do not share one database across project roots. Use stdlib SQLite, a schema version, and bounded typed payloads. `project_key` is an opaque project-scoped identifier, not a path or customer identifier; `feature_dir_key` is a normalized feature-directory key relative to the project root. Canonical task identity is `(project_key, feature_dir_key, stage_key, unit_key)`. Child records carry all four columns and use composite foreign keys; composite primary/unique keys include this tuple so task IDs and record IDs cannot collide across features. A proposed singleton `ledger_meta` row binds the database to its opaque `project_key`, schema version, and monotonically increasing database-wide `ledger_watermark`; each authority-changing commit advances that watermark transactionally, and durable host receipts/fence revisions bind to the relevant watermark.

- `task_ownership(project_key, feature_dir_key, stage_key, unit_key, task_id, stable_task_ref, lifecycle_revision, plan_revision, unit_checkpoint_revision, evidence_snapshot_fingerprint, owner_host, execution_id, generation, ownership_revision, evidence_revision, scope_ref, integrity_state, updated_at, PRIMARY KEY(project_key, feature_dir_key, stage_key, unit_key), UNIQUE(project_key, feature_dir_key, stage_key, unit_key, task_id))` - current recovery ownership and revision snapshot.
- `transfer(project_key, feature_dir_key, stage_key, unit_key, transfer_id, status, expected_generation, expected_owner_revision, previous_generation, new_generation, prior_execution_id, tenant_ref, decision_digest, scope_digest, evidence_revision, host_receipt_ref, host_receipt_digest, created_at, updated_at, PRIMARY KEY(project_key, feature_dir_key, stage_key, unit_key, transfer_id), FOREIGN KEY(project_key, feature_dir_key, stage_key, unit_key) REFERENCES task_ownership)` - idempotent transfer identity, pending/fenced/final states and receipt binding.
- `transition(project_key, feature_dir_key, stage_key, unit_key, transition_id, transfer_id, expected_generation, new_generation, from_revision, to_revision, decision_ref, outcome, correlation_id, created_at, PRIMARY KEY(project_key, feature_dir_key, stage_key, unit_key, transition_id), FOREIGN KEY(project_key, feature_dir_key, stage_key, unit_key) REFERENCES task_ownership)` - append-only history; the scoped transfer ID supports idempotent reconciliation.
- `checkpoint(project_key, feature_dir_key, stage_key, unit_key, checkpoint_id, sequence, scope_ref, evidence_revision, eligibility, payload_digest, created_at, PRIMARY KEY(project_key, feature_dir_key, stage_key, unit_key, checkpoint_id), FOREIGN KEY(project_key, feature_dir_key, stage_key, unit_key) REFERENCES task_ownership)` plus `evidence(project_key, feature_dir_key, stage_key, unit_key, evidence_id, checkpoint_id, kind, digest, source_ref, observed_at, PRIMARY KEY(project_key, feature_dir_key, stage_key, unit_key, evidence_id), FOREIGN KEY(project_key, feature_dir_key, stage_key, unit_key, checkpoint_id) REFERENCES checkpoint)` - checkpoint claims and evidence revision references.
- `recovery_audit(project_key, feature_dir_key, stage_key, unit_key, event_id, transition_id, event_type, actor_provenance_ref, decision_ref, evidence_revision, bounded_details, correlation_id, created_at, PRIMARY KEY(project_key, feature_dir_key, stage_key, unit_key, event_id), FOREIGN KEY(project_key, feature_dir_key, stage_key, unit_key) REFERENCES task_ownership)` - redacted audit references, no raw payloads.

A transfer starts in a SQLite `BEGIN IMMEDIATE` transaction: compare expected owner generation/revision and evidence revision for the composite task key, verify authorization binding, insert a task-scoped unique `TRANSFER_PENDING` ID and decision digest, advance the ledger watermark, then commit. Only then request host exclusion. The receiving host re-verifies authorization, tenant, expiry/currentness and exact transfer binding, durably fences the prior task+execution+generation, and returns a durable receipt. A second SQLite `BEGIN IMMEDIATE` transaction verifies the same pending ID, expected revisions and receipt binding, then stores receipt/final generation with ownership, transition history and recovery_audit records. Only after both durable host receipt and DB final commit may launch proceed. The DB step is atomic only within SQLite; no cross-system atomic transaction is claimed. A crash between host fence and DB final commit leaves old generation fenced and new unlaunched; recovery queries/replays the same idempotent transfer ID and never reopens old. If adapter cannot persist/enforce fence and receipt across restart, block. Each recovery-core write must use the same DB and expected-generation comparison. Legacy code not checking this DB is outside the fence; SQLite cannot stop arbitrary/non-cooperating writers or external effects.

SQLite serialization/durability assumptions and exact settings are specified below for the single project-root DB. `BEGIN IMMEDIATE` serializes writers across features in that project; lock contention/busy outcomes are bounded and never imply takeover. Separate project roots use separate databases and are isolated; a shared cross-project DB, network/synced copies, NFS/SMB, replicas, and cross-host locking are unsupported. Human approval is not an exclusion capability.

Crash outcomes: a crash before the first DB commit leaves no transfer record and permits no launch; after `TRANSFER_PENDING`, launch remains prohibited and recovery uses the same ID. A crash after the host durably fences but before DB final commit leaves old generation fenced/new unlaunched; query/replay that same idempotent ID, never reopen old. If adapter cannot ensure fence/receipt persistence and enforcement across restart, block. A crash after DB final commit but before response is resolved by transfer ID without a second generation change. These states do not form a cross-system atomic transaction. Malformed/torn/corrupt DB or receipt, failed recovery, unsupported schema or ambiguous outcome => unknown/blocked; do not infer rollback or reconstruct ownership from files. SQLite recovery is not proof of worker liveness.

Compatibility boundary: existing `state.json` and `state.md` are independently atomically replaced lifecycle-state files, and `audit.jsonl` has its own append/hash-chain behavior. They are not updated in the SQLite transaction and cannot be atomically consistent with it. Recovery ownership and recovery audit are authoritative in SQLite; No projection consumer, delivery payload or mirroring is defined or included in this increment. Existing lifecycle data is not authoritative input for recovery ownership; any import would require separate review. Lifecycle-file divergence is explicit, not disguised as cross-store consistency.

## Relationships and transitions

A task has one recovery ownership/generation, ordered checkpoints, observations and proposals. Its canonical task key is `(project_key, feature_dir_key, stage_key, unit_key)`, where the feature directory is relative to one receiving project root; the opaque project key and relative feature key prevent cross-project/feature key collisions. The reference also binds applicable lifecycle/plan/unit checkpoint revision/fingerprint. Authorization and decision bind tenant/principal, action/task/scope, nonce, evidence/revision and owner generation. Transition: `owner(n) -> TRANSFER_PENDING` via SQLite against expected owner generation/revision; host durably fences the prior task/execution/generation and returns the bound receipt; SQLite final commit stores receipt/new generation/transition history/recovery_audit; only then may the new generation launch. A crash between host fence and DB commit leaves old fenced/new unlaunched; same-ID query/replay reconciles, never reopens old. No cross-system atomicity is claimed. The DB fence covers enrolled core writers only, not arbitrary legacy code or external effects. Otherwise transfer blocks. Checkpoints require evidence/order/current-state validation; relevant changes invalidate dependent claims. Existing lifecycle files, audit and unit checkpoints remain separate evidence inputs until explicit integration. A mismatch/change between evidence snapshot and attempted resume invalidates dependent claims and blocks. Status labels source/revision, stale/unknown when unaligned. Unknown side effect awaits receiving-host reconciliation.

## Privacy and boundary rules

Persist only opaque IDs (including the project key), digests, timestamps, bounded reason codes, capability outcomes, safe evidence references and provenance references. Never put project paths, customer names, account numbers, balances, raw prompts, credentials, secrets or unnecessary payloads in keys, logs, audit, checkpoints, review package or tests. The one DB belongs to and is permissioned within its receiving project root; separate roots use separate DBs, with no cross-project shared store. Require root-contained canonical paths, least privilege, symlink/junction/reparse race defenses, bounded schema/evidence sizes, explicit version handling and safe errors. Receiving project enforces authentication, tenant authorization and governance, and owns access, retention and integrity policy. The receiving host verifies `AuthorizationContext` expiry/currentness and task/scope/revision/generation bindings before exclusion. The SQLite ledger does not override those policies. `workflow dispatch` is eligibility only, not ownership or execution. Only callers routing launch and all recovery-relevant mutations through the cooperative core are supported; arbitrary CLI/plugin/legacy paths and unenrolled writers are outside scope, and universal gating is explicitly deferred. No real host integration supports safe execution; all actual transfer is blocked.

## Proposed SQLite durability and recovery envelope

Pending human review, use one local-file database at the receiving project root only (shared across that project's features; never shared across project roots): `PRAGMA journal_mode=DELETE`, `PRAGMA synchronous=FULL`, `PRAGMA foreign_keys=ON` on every connection, and `PRAGMA busy_timeout=250` (milliseconds, proposed maximum). Verify the effective settings before use; mismatch or inability to enforce them blocks mutations. Bound lock wait by the smaller of 250ms and remaining caller deadline; if no budget remains, do not start a transaction. Use `BEGIN IMMEDIATE` and expected-generation/revision checks for every write transaction; no unbounded busy retries. `SQLITE_BUSY`/`SQLITE_LOCKED` returns a bounded conflict/blocked result, never takeover authority. Both pending and final transfer commits follow this profile. Final commit changes only the transfer receipt/status, recovery ownership, transition history and `recovery_audit` records; checkpoint/evidence changes are separate validated ledger transactions, not delivery work.

Durability assumes a local filesystem with correct SQLite locking, atomic journal handling, directory operations and truthful flush/fsync behavior, and storage/controller hardware honoring flushes (including power-loss behavior). `FULL` plus DELETE journaling provides SQLite's crash-recovery envelope under those assumptions, not protection against lying caches, failed media, privileged rewriting or arbitrary hardware/filesystem loss. No shared/network filesystem (NFS/SMB), cloud-synced directory, live copied DB, independent replica or cross-host durability/locking guarantee. No WAL profile is proposed. SQLite rollback/hot-journal recovery must be performed by SQLite, never by manually deleting journal files; unresolved recovery, corruption, failed integrity check or ambiguous commit => unknown/blocked, no launch.

Online backups use SQLite's online backup API to a protected destination within approved receiving-project policy during a quiesced window that stops enrolled launches/mutations across all features in that project, settles or explicitly reconciles pending transfers, preserves the source DB and journal, validates snapshot integrity, and records schema/version, safe generation/revision references, and the database-wide ledger watermark. Do not copy a live DB file or discard its journal. Backup access/retention are project policy; a backup is not a second writable authority and remains bound to its source project root/key. Restore is offline and fail-closed: it cannot authorize transfer unless a capable receiving host confirms durable fences and revisions against the restored DB watermark and reconciles every pending/committed transfer/receipt as needed. If host watermark/revisions are ahead of the snapshot, they must be reconciled into a consistent state before any launch or transfer. A DB backup cannot restore host fence state or reverse external effects; older snapshots may hide newer generations/decisions/watermarks, and monotonic rows alone cannot detect whole-DB rollback. If a trusted host cannot confirm durable fence/revision state against the watermark, or reconciliation is incomplete, remain blocked and do not launch or transfer. No real host integration currently provides this capability, so a restored DB cannot authorize transfer until reconciliation by a capable host is available; absent that host, it stays blocked. Never revive an old generation or rebuild authority from lifecycle files.

No outbox table, delivery payload, projection or consumer is included. Existing `audit.jsonl` is NOT mirrored or updated as part of either SQLite transfer transaction; it is a separate lifecycle artifact and is not authority for recovery transfer. Operational telemetry is best-effort observation, not an alternate ownership store or delivery protocol.

Persist correlation IDs in transition and `recovery_audit` records. No payloads, secrets, customer data, raw exceptions or identity/evidence text in telemetry; no identifiers as metric labels. Sink failure never changes ownership or grants launch.
