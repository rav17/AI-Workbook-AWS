# Recovery Core and Host Adapter Contract (Proposed)

Planning proposal for human review, not an implementation, supported-host qualification or measured assurance; the required behavioral guarantee is specified below. Approved specification remains WHAT. Q1 requires durable host-issued identity/fencing receipts and unsupported hosts to block; Q2 requires matching evidence and bindings, dependent invalidation, and blocking ambiguity. Exact protocol and fingerprint choices remain planned designs, not additional human-selected details. Q3 is deferred/out of scope with no autonomy grant. Proposed 10s total status/wait default and 2s per-adapter-call cap are unmeasured, testable defaults, not an approved SLO. Core is deterministic and model-free; no implicit command/plugin execution, AWS/cloud dependency, or policy transfer. Windows recovery-adapter execution and supervision are unsupported and out of scope: reject before any adapter child execution, call or worker spawn; no Windows status timeout or transfer is supported. Windows authoring/review and pure model/contract tests without adapter execution or spawn remain possible. The current supported-host set is empty and all actual transfers are blocked everywhere.

## Semantic operations

1. `observe(task, deadline)` -> status among `running|delayed|unavailable|unknown`, latest available owner/progress, evidence status, source/time/limits. Foreground returns by configured monotonic deadline for every admitted supported operation, using preloaded cache on missing/late data and without requiring child reap; missing host data is not death evidence.
2. `evaluate_resume(task, current_state)` -> latest eligible checkpoint or blocked/unknown under FR-007/008 and unambiguous progression order. No last-saved fallback; no replay for unknown side effect.
3. `propose_recovery(task, scope)` -> immutable decision package, no ownership mutation. Present decision/scope/readable evidence/status, actual verification/review status, unknowns, provenance expectations, exact allowed/excluded actions.
4. `commit_recovery(proposal, authenticated_decision, authorization_context)` -> accepted/rejected/stale/blocked. Transfer is a two-phase, idempotent protocol, not a cross-system atomic transaction. First use SQLite `BEGIN IMMEDIATE` to compare expected owner generation/revision and evidence revision and commit `TRANSFER_PENDING` with a unique transfer ID and decision digest. The receiving host verifies the bound authorization and currentness, durably fences the prior task+execution+generation, and returns a durable receipt bound to feature/task, tenant, previous/new generation, execution, exact decision/scope/evidence revision and transfer ID. Then use a second SQLite transaction to verify the same pending ID and receipt binding and persist receipt/final generation with ownership, transition history and recovery_audit records. New generation cannot launch until both the durable host receipt and DB final commit exist. Every enrolled core write checks generation in its DB transaction. SQLite alone does not establish host exclusion or stop arbitrary/non-cooperating writers/external effects.

## Adapter requirements

- **Identity**: stable host-issued identity bound to task and unique execution instance. Missing/mismatched/ambiguous/spoofed => unknown/blocked.
- **Observations**: distinct advisory outcomes and evidence time/source. Heartbeat expiry, absent host listing, timeout, delay or unavailable host must never prove death or authorize transfer.
- **Durable records**: typed, versioned, bounded; atomic compare-update/serializable transaction for owner, generation and revision. File atomic replace alone is insufficient. Torn/corrupt records, permission failure, rollback or ambiguous recovery => block.
- **Exclusion/fence and durable handoff**: SQLite generation checks fence only mutations by enrolled writers consulting the same receiving-project-root ledger; that one DB is shared across features within the project and writers serialize across them. Each project root has a separate DB, not a shared cross-project store. Composite task keys `(opaque project_key, project-relative feature_dir_key, stage_key, unit_key)` namespace ownership and child rows. This does not prove remote death or fence arbitrary/non-cooperating writers or external effects. Before a new generation may launch, the receiving host must durably exclude/fence the exact prior task+execution+generation and maintain that exclusion across host/adapter restart. Its receipt must be durable and bound to feature/task, tenant, previous/new generation, execution, exact decision/scope/evidence revision and unique transfer ID. A SQLite `TRANSFER_PENDING` row is committed first using expected owner generation/revision; host fencing follows; receipt and final generation are committed in SQLite afterward with ownership/transition history/recovery_audit. This is not a cross-system atomic transaction. If a crash occurs after host fencing but before the final DB commit, the prior generation remains fenced and the new generation remains unlaunched. Recovery queries or idempotently replays the same transfer ID to reconcile, never reopens the prior generation. If the adapter cannot guarantee persistent enforcement and durable receipt/query-or-idempotent-replay across restart, block. No real host integration currently supports safe execution, so all actual transfer is blocked; human approval and a successful SQLite transaction cannot substitute.
- **Timing and isolation (PROPOSED; subject to human plan approval and host/platform validation)**: every adapter invocation runs in a killable child controlled by a responsive parent supervisor, not inline or merely in a cancellable thread. The human-proposed 2s adapter cap and overall 10s monotonic status/wait default share the budget as specified below; cleanup completion is not a prerequisite to status return. The detailed admission, termination/reap, no-overlap, quarantine and same-ID reconciliation rules below are mandatory for this proposed supported-host contract; values are not accepted/measured SLOs or universal guarantees.
- **Authorization and approval**: define `AuthorizationContext` as receiving-project-authenticated principal and tenant, exact action/task/scope, decision nonce, evidence/revision and expected owner generation/revision, expiry/currentness data, and an opaque provenance reference. The receiving host verifies authorization, tenant, expiry and currentness before fencing and binds that context to the unique transfer ID and receipt. Persist only opaque provenance references; actor strings are not credentials. Missing identity, tenant mismatch, stale/replayed decision/nonce, or mismatched task/scope/evidence/revision/generation => block. Human approval cannot substitute for host exclusion.
- **Record/path safety**: root-contained canonical paths, least privilege, symlink/junction/reparse race defenses, size/schema limits and safe errors; never execute record/config commands.
- **Privacy**: synthetic tests; minimal redacted metadata. No customer data, raw prompts, credentials, secrets or unnecessary payload in logs/checkpoint/review/audit.

## PROPOSED invocation supervision and deadline contract

This generic proposal is not implemented, validated or approved and does not qualify any platform. All adapter operations require the isolation below. Parent alone authorizes ledger transitions and launch; children cannot commit recovery ownership or launch executions. Windows is excluded unconditionally before adapter child execution; qualification of Windows is outside this increment.

**FR-003 behavioral resolution (plan-11; design proposal, not implementation evidence).** The caller-facing status API is owned by a responsive foreground request supervisor. It starts the monotonic deadline before admission: `D = request_start + configured_wait`. Every admitted supported status operation either returns a validated current result before D or returns the latest preloaded owner/progress/evidence cache as `unavailable`/`unknown`, with evidence age, source/revision, uncertainty and safe next options, no later than D. The wait ends by D even when a contained status child has not exited or been reaped. FR-003 is the user-visible response deadline, not a complete-resource-cleanup deadline.

The foreground reads a bounded immutable in-memory snapshot (including an explicit empty/unknown snapshot), prepared before request admission and updated by nonblocking publication; it never acquires the ledger/cache-writer lock or performs adapter/host I/O. Bound admission, polling, result validation, rendering and output handoff; reject oversized input/results. All host adapter calls, including identity, status, fence and receipt queries, run in validated contained child processes. Ledger I/O/guard persistence, containment-controller operations and telemetry are off the foreground path with bounded nonblocking messages; an unavailable/full queue yields cached status, not a wait. No blocking adapter call, child join/reap, ledger lock, cleanup, telemetry sink, logging flush or fresh database write is required for returning, at or after D (nor may one consume the response reserve). Do not invoke arbitrary logging handlers on this path. Late results do not retroactively change the returned observation.

Before status waiting begins, validate a positive finite configured wait, a maximum response size and a bounded output channel with capacity reserved for the fixed response and a nonblocking enqueue/caller return. Prevalidate a fixed bounded template and the minimum rendering/handoff reserve for the target platform; prebuild a fixed bounded empty/unknown response before the request. Reject configuration or request before status waiting if its configured deadline or actual remaining time at admission cannot accommodate that verified reserve, if response/channel capacity cannot be assured, or if the platform cannot prove the required bound. Reject known blocked, uncontained or non-cooperative adapters before supported status admission; unsupported Windows is rejected before any adapter call or spawn. Never admit a non-cooperative adapter call inline; every admitted invocation runs in an isolated contained child. Such rejection is not an admitted status request and is not reported as meeting D. The bounded immutable snapshot is prepared before admission; if absent or invalid, use the prebuilt fixed empty/unknown response, without database access or logging during handoff.

Reserve `R` from D and begin fixed bounded rendering/nonblocking enqueue or caller return no later than `D-R`. Human-proposed 10s total and 2s adapter cap remain unmeasured, non-SLO defaults. Architect-proposed `R=250ms` is only a candidate for a verified minimum rendering/handoff reserve, not a guarantee by assumption; if the target platform cannot prove the selected reserve, it is unsupported. At adapter admission time t, `call_end = min(t + configured_adapter_cap, D-R)`. Before creating an invocation guard, compare remaining time to a prevalidated minimum useful budget for guard confirmation, contained creation and useful adapter work. If `D-R` is nonpositive, `D-R <= t`, or remaining time is insufficient, do not create a guard or spawn: immediately return the prebuilt cache as unavailable/unknown by D. If guard confirmation arrives too late after an initially sufficient budget, do not spawn; retain/reconcile any unresolved guard rather than claiming none exists. Admission/guard persistence, contained creation, work and any inline terminate/reap effort share the per-call budget. Stop work on timeout (or earlier if electing cleanup effort); request cancellation/termination with bounded polls only until call_end. The proposed 500ms caps inline cleanup effort within remaining call time, never delays response and never requires successful reap before return. Optional safe-read retries require confirmed prior tree death/resource cleanup, outcome reconciliation and sufficient useful budget.

Before adapter code executes, a trusted controller must have verified persistent parent-owned killable process-tree containment and durably persisted the active task/adapter guard. An unresolved active guard already blocks after a failed quarantine write; status return never waits for a new write. At timeout/unconfirmed cleanup retain containment and logically quarantine against that durable guard; a contained child may continue temporarily, under bounded secondary cleanup supervision, without delaying status. No new same-task adapter call, retry, ownership mutation, transfer or execution launch (including through another adapter) until the tree/pending creation is confirmed dead and cleaned and the outcome reconciled. Cache-only status remains available while quarantined and launches no child. A guarded same-transfer-ID outcome query may be admitted only after local cleanup as reconciliation, never as ordinary retry or permission to launch. Fence/transfer ambiguity remains blocked with the same transfer ID; remote effects may continue and the prior fence is never reopened.

Admission rejects unsupported platforms before execution, without invoking an unqualified child. Qualification requires the ability to sustain a responsive foreground supervisor, bounded response handoff and persistent containment; known inability means unsupported, not an admitted operation with a waived deadline. Catastrophic caller-process loss or an unavailable/frozen OS cannot provide any software response: this is outside operating preconditions, not a feature guarantee or a claim that such calls met D. Adapter hangs, ledger contention, sink stalls and delayed reap are isolated failures within the supported design and do not excuse missing D. Windows adapter execution/supervision remains unsupported and out of scope; the current supported-host set is empty and all actual transfers remain blocked. No platform is qualified and no timing/test success is claimed.

### Guard and containment enforcement

Trusted preflight verifies evidence-backed `controllable_child_creation`, `tree_termination_confirmed`, responsive-foreground capability and bounded nonblocking controller/IPC behavior for the exact adapter/launcher/platform, without executing an unqualified child. Containment must precede adapter bootstrap/imports and control pending/late creation, descendants and parent loss without an uncontained interval; a declaration is not proof. No helper-thread, ordinary multiprocessing or uncontained fallback. Bound child count, IPC sizes and handles. Children cannot commit ownership or launch executions. If late guard persistence completes after the spawn cutoff, the controller must not execute a child; retain/reconcile any unresolved guard.

Cancellation/termination requests never close containment handles before complete tree/no-child evidence; PID exit alone is insufficient. Secondary cleanup releases pipes, connections, buffers, artifacts and handles only when safe; child finally/atexit is not reliable. Every ownership/launch transaction atomically checks all unresolved task guards across adapters under ledger serialization. Restart treats active/pending/quarantined guards as blocked, never expired/dead. Keep persistent killable containment through foreground return and across parent loss as required by the host; quarantine is an admission block, not containment. Missing/failed containment invalidates support and blocks new work; status still uses cache while the caller remains available.

For fence operations persist TRANSFER_PENDING and transfer ID before invoking the child. Lost response/timeout/kill never authorizes fresh-ID retry, prior-fence reopening or launch. After local tree death/cleanup, use guarded same-ID authoritative outcome lookup; any idempotent same-ID replay is explicit reconciliation with current authorization, not ordinary timeout retry. Unknown remote outcome remains blocked. Services enforce that transfer ID as idempotency key and finite operation deadlines across restart; derive remaining duration rather than compare unrelated hosts' monotonic clocks. Local kill cannot cancel remote effects.

## Outcomes and constraints

`running` is affirmative current execution observation, not proof all others excluded. `delayed` is scheduled/waiting, not takeover permission. `unavailable` means required observation inaccessible; last-known owner/progress marked as such. `unknown` means incomplete/stale/ambiguous/conflicting/timed-out/unresolved evidence or identity. `blocked` means ownership action lacks required capability, provenance, evidence or exclusion. Known blocked, uncontained or non-cooperative adapters are rejected before supported status admission; unsupported Windows is rejected before any adapter call or spawn. Non-cooperative calls are never admitted inline. Every admitted invocation runs in an isolated contained child; for every admitted supported status operation the foreground returns by D, independently of adapter behavior, child exit, reap or cleanup, using the prebuilt immutable bounded cache (or the explicit fixed bounded empty/unknown response) when current evidence is unavailable. No outcome implies stopped/dead by default.

## Non-guarantees

Liveness signals alone do not prove death; approval alone cannot replace safe exclusion. Generation fencing applies only to writers that atomically validate it. Local SQLite transactional fencing applies only to cooperating core writers; it does not prove remote worker death and gives no fence over arbitrary legacy code/external effects. No exactly-once effect promise. Approval cannot substitute for host exclusion. Receiving project enforces authentication, tenant authorization and governance, and owns retention/access/integrity and deployment decisions. SQLite does not confer those permissions. Unsupported hosts remain unsupported.

## Proposed SQLite durability and recovery envelope

Pending human review, use one local-file database at the receiving project root only, shared across that project's features and never across project roots: `PRAGMA journal_mode=DELETE`, `PRAGMA synchronous=FULL`, `PRAGMA foreign_keys=ON` on every connection, and `PRAGMA busy_timeout=250` (milliseconds, proposed maximum). Verify the effective settings before use; mismatch or inability to enforce them blocks mutations. Bound lock wait by the smaller of 250ms and remaining caller deadline; if no budget remains, do not start a transaction. Use `BEGIN IMMEDIATE` and expected-generation/revision checks for every write transaction; no unbounded busy retries. `SQLITE_BUSY`/`SQLITE_LOCKED` returns a bounded conflict/blocked result, never takeover authority. Both pending and final transfer commits follow this profile. Final commit changes only the transfer receipt/status, recovery ownership, transition history and `recovery_audit` records; checkpoint/evidence changes are separate validated ledger transactions, not delivery work.

Durability assumes a local filesystem with correct SQLite locking, atomic journal handling, directory operations and truthful flush/fsync behavior, and storage/controller hardware honoring flushes (including power-loss behavior). `FULL` plus DELETE journaling provides SQLite's crash-recovery envelope under those assumptions, not protection against lying caches, failed media, privileged rewriting or arbitrary hardware/filesystem loss. No shared/network filesystem (NFS/SMB), cloud-synced directory, live copied DB, independent replica or cross-host durability/locking guarantee. No WAL profile is proposed. SQLite rollback/hot-journal recovery must be performed by SQLite, never by manually deleting journal files; unresolved recovery, corruption, failed integrity check or ambiguous commit => unknown/blocked, no launch.

Online backups use SQLite's online backup API to a protected destination within approved receiving-project policy during a quiesced window that stops launches/mutations across all features in that project, settles/reconciles pending transfers, preserves the source and journal, validates integrity, and records schema/version, safe revisions and the monotonic DB-wide watermark. A backup is not a second writable authority and remains bound to its source project root/key. Restore is offline and fails closed: it cannot authorize transfer unless a capable host confirms durable fences and revisions against the restored DB watermark and reconciles pending/committed transfer receipts. A backup cannot restore host fence state or reverse effects; a stale snapshot may omit newer generations/decisions, and monotonic rows alone cannot detect whole-DB rollback. If trustworthy host confirmation/reconciliation is unavailable, do not launch or transfer. No real host integration currently provides this capability, so restored DBs cannot authorize transfer until a capable host completes reconciliation; otherwise they remain blocked. Never revive an old generation or rebuild authority from lifecycle files.

No outbox table, delivery payload, projection or consumer is included. Existing `audit.jsonl` is NOT mirrored or updated as part of either SQLite transfer transaction; it is a separate lifecycle artifact and is not authority for recovery transfer. Operational telemetry is best-effort observation, not an alternate ownership store or delivery protocol.

## Privacy-safe observability proposal

Required before production, not implemented or satisfied by existing lifecycle audit: inject a host `TelemetrySink` with bounded `emit_event`, `increment`, `observe` and `span` operations. A stdlib seam (`logging` with allowlisted JSON formatting, `uuid` correlation IDs, `time.monotonic` durations and `contextvars` propagation) supplies structured events and timing hooks without a new dependency. Host adapters must provide approved metric and trace sinks/exporters; stdlib logging alone does not provide production metrics or distributed tracing. Missing exporters/cross-host propagation are explicit host limitations and production blockers, not satisfied facilities. The core must report capabilities without secrets. Sink calls are nonblocking/bounded, never extend the operation deadline; sink failure is reported as `telemetry_unavailable` through a safe fallback/capability result, never changes ledger authority or permits launch. No durable telemetry delivery guarantee.

Generate an opaque `correlation_id` per request; propagate it plus validated bounded trace context to adapter calls, retry and same-ID reconciliation. Persist correlation ID in `recovery_audit` and transition records; correlate across retries with opaque transfer ID, never credentials. Structured event allowlist: schema version, UTC timestamp, correlation/trace/span IDs, operation enum, outcome/reason enums, duration_ms, retry_count and optional opaque transfer reference/generation/revision. Do not emit tenant/principal/task identifiers, paths, evidence/command text, prompts, payloads, receipt contents, raw exceptions, customer data or secrets. Audit retains only approved opaque provenance/evidence references. Validate/redact before the sink; reject unknown fields and truncate bounded counters, not sensitive strings.

Bounded outcomes: `running|delayed|unavailable|unknown|accepted|rejected|stale|blocked`. Bounded reasons: `ok|deadline_exceeded|identity_missing|authorization_invalid|evidence_invalid|capability_missing|exclusion_missing|receipt_invalid|generation_conflict|sqlite_busy|storage_corrupt|storage_unavailable|effect_unknown|telemetry_unavailable|internal_error`. Unknown errors map to `internal_error`, not free-form labels. Metrics: `recovery_status_total{outcome}`; `recovery_operation_duration_seconds{operation,outcome}`; `recovery_deadline_exceeded_total{operation}` and `recovery_deadline_remaining_seconds{operation}`; `recovery_sqlite_conflict_total{kind=busy|locked|generation_revision}`; `recovery_sqlite_transaction_duration_seconds{phase=pending|final|other,outcome}`; `recovery_transition_total{outcome,reason}` and `recovery_telemetry_drop_total{signal=log|metric|trace}` where the host sink is available. Operation labels are limited to `observe|evaluate_resume|propose_recovery|commit_recovery|reconcile`; no IDs/timestamps/arbitrary strings as metric labels. Export only aggregate durations/counts with bounded cardinality.

Trace root `recovery.<operation>` has child spans `adapter.identity`, `adapter.observe`, `evidence.validate`, `authorization.verify`, `sqlite.pending`, `adapter.fence`, `sqlite.final`, `adapter.receipt_query` as applicable. Record monotonic duration, bounded outcome/reason and correlation only; no SQL/bind values or payload capture, no unsafe baggage. Preserve same transfer correlation across interrupted-transfer reconciliation without claiming cross-system atomicity. Receiving project owns access, retention, sampling and approved destinations; no external exporter is configured here. Future fake-sink checks must assert event/audit correlation, outcome/reason bounds, status/deadline/conflict metrics, span parentage, redaction/cardinality and safe sink-failure behavior. These are planned checks, not executed results.
