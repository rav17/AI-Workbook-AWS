# Implementation Plan: Reliable Worker Recovery

**Branch**: `033-reliable-worker-recovery` | **Date**: 2026-11-14 | **Spec**: [spec.md](spec.md)
**Input**: Approved specification. Earlier human gate authorized planning only.

## Summary

Propose a host-neutral, model-free recovery core and narrow host-adapter contract for durable ownership/progress, bounded status, verified-checkpoint selection, human-reviewed decisions, and two-phase idempotent transfer among enrolled writers. The host must durably fence the prior task/execution/generation before SQLite final ownership commit; neither the receipt nor DB commit alone permits launch. No real host integration currently supports safe execution, so all actual transfer is blocked. Missing identity, evidence, authorization or exclusion blocks; uncertain liveness never means death and uncertain effects are never replayed. Provide 19/19 mapped portable synthetic scenarios. Windows recovery-adapter execution and supervision are unsupported and out of scope; Windows remains usable for authoring/review and pure model/contract tests without adapter execution or spawn. No broad harness rollout, models, cloud resources, money movement or customer-record updates.

## Proposed Architecture and State Flow

1. `speckit_flow/recovery/`: deterministic validated domain records and status/checkpoint/decision logic. No models, prompts, shell/plugin execution, cloud SDK or host policy.
2. Adapter protocol supplies task/execution-bound self identity, bounded status, durable record transaction and affirmative safe exclusion/fencing. Missing, unsupported, ambiguous or stale capability => blocked/unknown.
3. Transfer uses two durable phases. First SQLite commits `TRANSFER_PENDING` and a unique transfer ID/decision digest using expected owner generation/revision. The receiving host verifies authorization/currentness, then durably fences the prior task+execution+generation before any new execution is permitted and returns a receipt bound to feature/task, tenant, previous/new generation, execution, exact decision/scope/evidence revision and transfer ID. Second SQLite commits that receipt/final generation with ownership, transition history and recovery_audit records. Launch requires both receipt and DB final commit. A crash after host fencing but before final DB commit leaves old generation fenced and new unlaunched; recovery queries/replays the same idempotent transfer ID and never reopens old. If receipt/fence persistence across restart is not guaranteed, block. This is not a cross-system atomic transaction. All enrolled core writes compare generation; arbitrary/legacy writers and external effects are not fenced.
4. **FR-003 behavioral resolution (plan-11; design proposal, not implementation evidence).** The caller-facing status API is owned by a responsive foreground request supervisor. It starts the monotonic deadline before admission: `D = request_start + configured_wait`. Every admitted supported status operation either returns a validated current result before D or returns the latest preloaded owner/progress/evidence cache as `unavailable`/`unknown`, with evidence age, source/revision, uncertainty and safe next options, no later than D. The wait ends by D even when a contained status child has not exited or been reaped. FR-003 is the user-visible response deadline, not a complete-resource-cleanup deadline.

The foreground reads a bounded immutable in-memory snapshot (including an explicit empty/unknown snapshot), prepared before request admission and updated by nonblocking publication; it never acquires the ledger/cache-writer lock or performs adapter/host I/O. Bound admission, polling, result validation, rendering and output handoff; reject oversized input/results. All host adapter calls, including identity, status, fence and receipt queries, run in validated contained child processes. Ledger I/O/guard persistence, containment-controller operations and telemetry are off the foreground path with bounded nonblocking messages; an unavailable/full queue yields cached status, not a wait. No blocking adapter call, child join/reap, ledger lock, cleanup, telemetry sink, logging flush or fresh database write is required for returning, at or after D (nor may one consume the response reserve). Do not invoke arbitrary logging handlers on this path. Late results do not retroactively change the returned observation.

Before status waiting begins, validate a positive finite configured wait, a maximum response size and a bounded output channel with capacity reserved for the fixed response and a nonblocking enqueue/caller return. Prevalidate a fixed bounded template and the minimum rendering/handoff reserve for the target platform; prebuild a fixed bounded empty/unknown response before the request. Reject configuration or request before status waiting if its configured deadline or actual remaining time at admission cannot accommodate that verified reserve, if response/channel capacity cannot be assured, or if the platform cannot prove the required bound. Reject known blocked, uncontained or non-cooperative adapters before supported status admission; unsupported Windows is rejected before any adapter call or spawn. Never admit a non-cooperative adapter call inline; every admitted invocation runs in an isolated contained child. Such rejection is not an admitted status request and is not reported as meeting D. The bounded immutable snapshot is prepared before admission; if absent or invalid, use the prebuilt fixed empty/unknown response, without database access or logging during handoff.

Reserve `R` from D and begin fixed bounded rendering/nonblocking enqueue or caller return no later than `D-R`. Human-proposed 10s total and 2s adapter cap remain unmeasured, non-SLO defaults. Architect-proposed `R=250ms` is only a candidate for a verified minimum rendering/handoff reserve, not a guarantee by assumption; if the target platform cannot prove the selected reserve, it is unsupported. At adapter admission time t, `call_end = min(t + configured_adapter_cap, D-R)`. Before creating an invocation guard, compare remaining time to a prevalidated minimum useful budget for guard confirmation, contained creation and useful adapter work. If `D-R` is nonpositive, `D-R <= t`, or remaining time is insufficient, do not create a guard or spawn: immediately return the prebuilt cache as unavailable/unknown by D. If guard confirmation arrives too late after an initially sufficient budget, do not spawn; retain/reconcile any unresolved guard rather than claiming none exists. Admission/guard persistence, contained creation, work and any inline terminate/reap effort share the per-call budget. Stop work on timeout (or earlier if electing cleanup effort); request cancellation/termination with bounded polls only until call_end. The proposed 500ms caps inline cleanup effort within remaining call time, never delays response and never requires successful reap before return. Optional safe-read retries require confirmed prior tree death/resource cleanup, outcome reconciliation and sufficient useful budget.

Before adapter code executes, a trusted controller must have verified persistent parent-owned killable process-tree containment and durably persisted the active task/adapter guard. An unresolved active guard already blocks after a failed quarantine write; status return never waits for a new write. At timeout/unconfirmed cleanup retain containment and logically quarantine against that durable guard; a contained child may continue temporarily, under bounded secondary cleanup supervision, without delaying status. No new same-task adapter call, retry, ownership mutation, transfer or execution launch (including through another adapter) until the tree/pending creation is confirmed dead and cleaned and the outcome reconciled. Cache-only status remains available while quarantined and launches no child. A guarded same-transfer-ID outcome query may be admitted only after local cleanup as reconciliation, never as ordinary retry or permission to launch. Fence/transfer ambiguity remains blocked with the same transfer ID; remote effects may continue and the prior fence is never reopened.

Admission rejects unsupported platforms before execution, without invoking an unqualified child. Qualification requires the ability to sustain a responsive foreground supervisor, bounded response handoff and persistent containment; known inability means unsupported, not an admitted operation with a waived deadline. Catastrophic caller-process loss or an unavailable/frozen OS cannot provide any software response: this is outside operating preconditions, not a feature guarantee or a claim that such calls met D. Adapter hangs, ledger contention, sink stalls and delayed reap are isolated failures within the supported design and do not excuse missing D. Windows adapter execution/supervision remains unsupported and out of scope; the current supported-host set is empty and all actual transfers remain blocked. No platform is qualified and no timing/test success is claimed.

Exact fingerprint implementation is not a human-selected detail. Relevant changes invalidate dependent claims only; uncertain prior side effects are never automatically replayed.

### Proposed SQLite ledger and consistency boundary

Normalized/versioned rows all carry `(project_key, feature_dir_key, stage_key, unit_key)`. `task_ownership` uses those four columns as its composite primary key (and carries an opaque `task_id` alias plus stable reference and lifecycle/plan/unit revisions); each `transfer`, `transition`, `checkpoint`, `evidence`, and `recovery_audit` uses the same tuple in a composite foreign key to ownership and in a composite primary key with its local record ID. `transfer_id` and other record IDs are thus scoped, never global `task_id`-only keys. See complete proposed columns/constraints in `data-model.md`. Bound/redact payloads. The first DB transaction records `TRANSFER_PENDING` and unique transfer/decision digest using expected owner generation/revision. The host then durably fences prior task+execution+generation and returns a receipt bound to feature/task, tenant, old/new generation, execution, exact decision/scope/evidence revision and transfer ID. The second DB transaction commits receipt/final generation plus ownership, transition history and recovery_audit records. Launch requires both receipt and DB commit; never claim cross-system atomicity.

For the transfer's final phase, use `BEGIN IMMEDIATE`, compare the scoped pending transfer ID and expected generation/ownership/evidence revisions, validate the durable host receipt, then update ownership/generation and append transition history/recovery_audit in one SQLite commit. The first SQLite commit records `TRANSFER_PENDING`; it is not part of this final commit. SQLite writer serialization spans all features in the receiving project and is local concurrency control, not a distributed lock or safe-exclusion signal. Each receiving project root has its own DB; sharing across roots, network filesystems, independent DB copies and cross-host guarantees are unsupported.

Crash proposal: a pre-host crash leaves `TRANSFER_PENDING` but permits no launch; resume/reconciliation uses the same transfer ID. A crash after the host durably fences but before DB final commit leaves the old generation fenced and the new generation unlaunched; query/replay that same idempotent ID, never reopen the old generation. If the adapter cannot guarantee fence/receipt persistence and enforcement across restart, block. A crash after final DB commit may lose caller response, but lookup by transfer ID returns the committed result. These are safe separate-system states, not cross-system atomicity. Torn/corrupt DB/receipt, failed integrity/recovery, unsupported schema or ambiguous commit => unknown/blocked; never infer rollback or rebuild from mirrors. Existing lifecycle files remain separate.

## Proposed SQLite durability and recovery envelope

Pending human review, use one local-file database at the receiving project root only, shared across that project's features and never shared across project roots: `PRAGMA journal_mode=DELETE`, `PRAGMA synchronous=FULL`, `PRAGMA foreign_keys=ON` on every connection, and `PRAGMA busy_timeout=250` (milliseconds, proposed maximum). Verify the effective settings before use; mismatch or inability to enforce them blocks mutations. Bound lock wait by the smaller of 250ms and remaining caller deadline; if no budget remains, do not start a transaction. Use `BEGIN IMMEDIATE` and expected-generation/revision checks for every write transaction; no unbounded busy retries. `SQLITE_BUSY`/`SQLITE_LOCKED` returns a bounded conflict/blocked result, never takeover authority. Both pending and final transfer commits follow this profile. Final commit changes only the transfer receipt/status, recovery ownership, transition history and `recovery_audit` records; checkpoint/evidence changes are separate validated ledger transactions, not delivery work.

Durability assumes a local filesystem with correct SQLite locking, atomic journal handling, directory operations and truthful flush/fsync behavior, and storage/controller hardware honoring flushes (including power-loss behavior). `FULL` plus DELETE journaling provides SQLite's crash-recovery envelope under those assumptions, not protection against lying caches, failed media, privileged rewriting or arbitrary hardware/filesystem loss. No shared/network filesystem (NFS/SMB), cloud-synced directory, live copied DB, independent replica or cross-host durability/locking guarantee. No WAL profile is proposed. SQLite rollback/hot-journal recovery must be performed by SQLite, never by manually deleting journal files; unresolved recovery, corruption, failed integrity check or ambiguous commit => unknown/blocked, no launch.

Online backups use SQLite's online backup API to a protected destination within approved receiving-project policy during a quiesced window that stops launches/mutations across all features in that project, settles/reconciles pending transfers, preserves the source DB and journal, validates integrity, and records schema/version, safe revisions and the monotonic database-wide watermark. Do not copy a live DB file or discard its journal. Backup access/retention are project policy; a backup is not a second writable authority and remains bound to its source project root/key. Restore is offline and fail-closed: it cannot authorize a transfer unless a capable receiving host confirms durable fences and revisions against the restored DB watermark and reconciles every pending/committed transfer/receipt as needed. A DB backup cannot restore host fence state or reverse external effects; older snapshots may hide newer generations/decisions/watermarks, and monotonic rows alone cannot detect whole-DB rollback. If a trusted host cannot confirm durable fence/revision state against the watermark, or reconciliation is incomplete, remain blocked and do not launch or transfer. No real host integration currently provides this capability, so a restored DB cannot authorize transfer until reconciliation by a capable host is available; absent that host, it stays blocked. Never revive an old generation or rebuild authority from lifecycle files.

No outbox table, delivery payload, projection or consumer is included. Existing `audit.jsonl` is NOT mirrored or updated as part of either SQLite transfer transaction; it is a separate lifecycle artifact and is not authority for recovery transfer. Operational telemetry is best-effort observation, not an alternate ownership store or delivery protocol.

## Privacy-safe observability proposal

Required before production, not implemented or satisfied by existing lifecycle audit: inject a host `TelemetrySink` with bounded `emit_event`, `increment`, `observe` and `span` operations. A stdlib seam (`logging` with allowlisted JSON formatting, `uuid` correlation IDs, `time.monotonic` durations and `contextvars` propagation) supplies structured events and timing hooks without a new dependency. Host adapters must provide approved metric and trace sinks/exporters; stdlib logging alone does not provide production metrics or distributed tracing. Missing exporters/cross-host propagation are explicit host limitations and production blockers, not satisfied facilities. The core must report capabilities without secrets. Sink calls are nonblocking/bounded, never extend the operation deadline; sink failure is reported as `telemetry_unavailable` through a safe fallback/capability result, never changes ledger authority or permits launch. No durable telemetry delivery guarantee.

Generate an opaque `correlation_id` per request; propagate it plus validated bounded trace context to adapter calls, retry and same-ID reconciliation. Persist correlation ID in `recovery_audit` and transition records; correlate across retries with opaque transfer ID, never credentials. Structured event allowlist: schema version, UTC timestamp, correlation/trace/span IDs, operation enum, outcome/reason enums, duration_ms, retry_count and optional opaque transfer reference/generation/revision. Do not emit tenant/principal/task identifiers, paths, evidence/command text, prompts, payloads, receipt contents, raw exceptions, customer data or secrets. Audit retains only approved opaque provenance/evidence references. Validate/redact before the sink; reject unknown fields and truncate bounded counters, not sensitive strings.

Bounded outcomes: `running|delayed|unavailable|unknown|accepted|rejected|stale|blocked`. Metrics: `recovery_status_total{outcome}`; `recovery_operation_duration_seconds{operation,outcome}`; `recovery_deadline_exceeded_total{operation}` and `recovery_deadline_remaining_seconds{operation}`; `recovery_sqlite_conflict_total{kind=busy|locked|generation_revision}`; `recovery_sqlite_transaction_duration_seconds{phase=pending|final|other,outcome}`; `recovery_transition_total{outcome,reason}` and `recovery_telemetry_drop_total{signal=log|metric|trace}` where the host sink is available. Operation labels are limited to `observe|evaluate_resume|propose_recovery|commit_recovery|reconcile`; no IDs/timestamps/arbitrary strings as metric labels. Export only aggregate durations/counts with bounded cardinality.

Trace root `recovery.<operation>` has child spans `adapter.identity`, `adapter.observe`, `evidence.validate`, `authorization.verify`, `sqlite.pending`, `adapter.fence`, `sqlite.final`, `adapter.receipt_query` as applicable. Record monotonic duration, bounded outcome/reason and correlation only; no SQL/bind values or payload capture, no unsafe baggage. Preserve same transfer correlation across interrupted-transfer reconciliation without claiming cross-system atomicity. Receiving project owns access, retention, sampling and approved destinations; no external exporter is configured here.
