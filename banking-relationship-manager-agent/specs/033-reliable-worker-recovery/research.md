## Proposals and alternatives for human plan-gate decision

### Host-neutral core and bounded adapter (proposal; not yet accepted)
**Proposal**: deterministic semantics in `speckit_flow/recovery/`; adapter exposes stable task/execution-bound identity, advisory statuses, durable records, bounded operations and affirmative safe-exclusion/fencing. Missing capability blocks.
**Rationale**: `orchestration.dispatch` validates eligibility and leaves agent invocation to host; `state.atomic_write` replaces files individually. Neither establishes worker liveness, transactionality or mutual exclusion.
**Rejected**: heartbeat/listing/timeout as death; actor label as identity; AWS-specific service; claim local fencing can stop arbitrary legacy code.

### Status and deadline (Q1 human answer; timing defaults proposed)
**Human answer**: `human:rav17` requires durable host-issued identity/fencing receipts and unsupported hosts to block; the human proposes a 10-second total wait and 2-second adapter-call cap. **Planned design**: retain `running`, `delayed`, `unavailable`, `unknown`; apply the proposed supervision contract below. The timing values remain human-proposed, unmeasured, non-SLO defaults, not approval of implementation details.
**Rationale**: FR-002/003 distinguish statuses and require bounded wait; spec does not prescribe universal duration.
**Rejected**: infinite wait, treating timeout/unavailability as stopped, delayed as takeover authority, unreviewed universal SLO. Numeric values are proposals, not measured.

### Local durable ledger (proposal; human plan-gate decision pending)
**Proposal**: stdlib SQLite, one local database per receiving-project root at `.specify/recovery/recovery.sqlite3`, shared by that project's features and never shared across project roots. The directory/database are future-implementation proposals only; neither is created during planning. Task identity and every child-row relationship use composite keys `(opaque project_key, feature_dir_key relative to the project root, stage_key, unit_key)` rather than globally unique `task_id` alone. Ordinary writes use `BEGIN IMMEDIATE` and expected generation/revision checks. Transfers use two DB commits separated by host exclusion: pending ID/digest first, durable host fence/receipt second, then SQLite receipt/final generation plus history/audit. This is not one atomic transaction. Schema is specified in `data-model.md`.
**Rationale**: avoids a new dependency/service and provides local transactional updates; one DB per receiving root avoids feature-local DB fragmentation while keeping cross-project privacy/isolation. SQLite writer serialization applies across all features in one project and may yield bounded lock contention; it is not distributed exclusion. Portable only where SQLite local-filesystem locking/journaling assumptions hold.
**Bounds**: no network/shared/synced filesystems, distributed lock, independent replicas, cross-host CAS, or shared DB between project roots. Each receiving project owns its DB, permissions, retention and backup destination; keys contain opaque identifiers, not project paths or customer data. A trusted host must confirm durable fence/revisions against the DB-wide watermark after restore; absent that confirmation/reconciliation, restored state cannot authorize transfer. No current real host adapter supports safe execution or restore reconciliation, so actual transfers remain blocked.
**Consistency/crash proposal**: ledger is authoritative only for recovery ownership/transitions. Transfers use two durable phases: SQLite commits `TRANSFER_PENDING` with unique transfer ID/decision digest against expected owner generation/revision; host durably fences prior task/execution/generation and returns a receipt; SQLite then commits receipt/final generation with ownership, transition history and recovery_audit records. Launch is prohibited until both host receipt and DB final commit exist. This is not a cross-system atomic transaction. A crash after host fencing but before final DB commit leaves old generation fenced and new unlaunched; recovery queries/replays the same ID only, never reopens old generation. If durable receipt persistence/enforcement across restart is unavailable, block. Post-commit lost response is resolved by transfer ID. Corrupt/torn/ambiguous DB or receipt => unknown/blocked; never reconstruct ownership from mirrors. Existing `state.json`/Markdown and `audit.jsonl` are separate and not transactionally coupled. No projection delivery is in scope; no cross-file atomicity claim.
**Rejected**: abstract store without implementable proposal; process-local mutex, heartbeat lease, audit chain or approval as exclusion; treating host receipt plus SQLite update as atomic; reopening the old generation after interrupted transfer; network filesystem claims; SQLite as proof of liveness or arbitrary-code fencing.

### Authorization context (architect proposal; not a human answer or accepted decision)
**Proposal**: bind a receiving-project-authenticated principal and tenant to exact action/task/scope, decision nonce, evidence/revision and owner generation/revision. The receiving host verifies authorization, expiry and currentness before fencing. Persist only opaque provenance references; actor strings are not credentials. Missing identity, tenant mismatch, stale/replayed decision/nonce, or any task/scope/revision/generation mismatch blocks. Human approval cannot substitute for host exclusion.
**Rationale**: a task ID or actor label is not tenant authorization; the receiving project owns authentication and policy enforcement.
**Rejected**: accepting caller-supplied actor text as credential; reusing stale decisions; human approval as host fence.

### Bootstrap and lifecycle boundary (architect proposal; not a human answer or accepted decision)
A stable recovery reference binds the receiving-project-local feature/stage/unit key and applicable lifecycle/plan/unit checkpoint revision/fingerprint. `workflow dispatch` is eligibility only, not ownership or execution. A bounded seam in `orchestration.py` and `units.py` (or equivalent) must route actual launch and every recovery-relevant mutation through the cooperative core. SQLite is authoritative only for recovery owner/generation, transition history and recovery evidence/checkpoint binding. Existing `state.json`, `state.md`, `audit.jsonl` and `units.py` remain separate workflow artifacts until explicit integration, and are checked as evidence inputs. A mismatch/change between evidence snapshot and attempted resume invalidates dependent claims and blocks. Status labels source/revision, stale/unknown if unaligned. Only enrolled writers are supported; arbitrary CLI/plugin/legacy direct writes are outside scope, and gating them is explicitly deferred. No real host integration supports safe execution; all actual transfers remain blocked.

### Checkpoint evidence (Q2 human requirement; detailed design proposal)
**Human answer**: require matching completion evidence, relevant inputs/dependencies/instructions and verification bindings; invalidate affected dependents; block ambiguous progress or side effects. **One planned specification-conforming design**: identify scope, criteria, claim, accessible evidence per criterion and applicable verification/result; select latest only by unambiguous progression order. Bind to canonical relevant input/transitive dependency/instruction/command/environment/verification evidence. Relevant change invalidates dependent claims only; unrelated progress preserved. Ambiguity blocks; uncertain external effects are not replayed. Exact fingerprint implementation details were not selected by the human.
**Rationale**: FR-007/008 and product assumptions; `units.py` offers only a partial precedent (dependency graph, tracked file and command digests).
**Rejected**: last-saved resume, timestamp guesses, global invalidation, unrelated passing test as proof, replaying uncertain effects.

### Human approval/provenance
**Specification requirement / plan proposal**: per-decision human authorization; bind to scope/evidence revision/generation; reject stale/replayed. Receiving host establishes identity; actor label is not proof. Q3 is explicitly deferred/out of scope by the recorded human answer and grants no autonomy or authorization.
**Rationale**: FR-010 through FR-013. `audit.py` hash chain is not human authentication or privileged tamper prevention; compliance says receiving project owns tenant/auth.
**Rejected**: autonomy, actor strings, approval bypassing evidence/fencing, payload logging.

### Portable scenario tests
**Proposal**: use existing `speckit_flow` unit tree; deterministic model-free cases mapped independently to 19/19 classes. Reuse bootstrap tests only for governance/optional-pack claims they actually exercise.
**Rationale**: existing tests cover intent, dispatch eligibility, unit checkpoint basics and bootstrap governance; not this recovery contract.
**Rejected**: broad multi-harness/swarm, live/cloud test dependency, inferring new coverage from unrelated tests.

## Storage scope and durability proposal

Pending human review: one local SQLite database at each receiving-project root, shared among that project's features; separate roots have separate DBs and no cross-project shared database. Composite task keys and project privacy boundaries are specified in `data-model.md`. Use `journal_mode=DELETE`, `synchronous=FULL`, foreign keys ON per connection, busy timeout <=250ms capped by remaining deadline, and `BEGIN IMMEDIATE`; writers serialize across features. Network/synced filesystems and cross-host guarantees are unsupported. Use SQLite's online backup API during an approved quiesced window, not live file copies. Restores fail closed unless a capable host confirms durable fences/revisions against the DB watermark and reconciles receipts; no current real host supports this, so restored DB transfer authorization remains unavailable. Whole-DB rollback is not detectable from monotonic rows alone. Full assumptions and boundaries are in `data-model.md` and the adapter contract.

Final SQLite transfer commit includes only transfer receipt/status, recovery ownership, transition history and `recovery_audit` records. No outbox table/payload/projection/consumer is included. Existing `audit.jsonl` is NOT mirrored or updated by this transaction: it remains a separate lifecycle artifact, not authority for recovery transfer. Removing undefined delivery work avoids an unowned consumer/retry protocol; adding it requires separate review.

## Observability boundary (proposal, not satisfaction)

Use the host `TelemetrySink`/stdlib logging, monotonic timing and context propagation seam defined in `contracts/recovery-adapter.md`: opaque correlation/trace IDs, allowlisted bounded reason/outcome codes, status/deadline/SQLite conflict and duration metrics, and spans for observation, evidence/auth, pending commit, host fence/receipt reconciliation and final commit. Persist correlation IDs in transition and `recovery_audit` records. No payloads, secrets, customer data, raw exceptions or identity/evidence text in telemetry; no identifiers as metric labels. Sink failure never changes ownership or grants launch. Missing metric/trace exporters or cross-host propagation are explicit host limitations and required before production, not constitutional satisfaction. Fake-sink validation is future-only; no execution claim.

### Delivery scope decision (proposal pending human review)
**Proposal**: omit the outbox table, delivery payload and projection consumer entirely; final transfer transaction commits receipt/status, recovery ownership, transition history and recovery_audit only.
**Rationale**: no consumer or required projection contract exists; existing lifecycle audit.jsonl is separate and is not recovery-transfer authority. A redacted host telemetry sink is observability, not delivery or mirrored audit.
**Rejected**: retain undefined optional delivery work, silently mirror audit.jsonl, or imply cross-file transactionality. Any future projection requires a separately reviewed consumer/retry/idempotency/retention contract and tests.

### Plan-10 decision: exclude Windows execution (scope boundary)
**Decision**: Windows recovery-adapter execution and supervision are unsupported and out of scope in this increment; fail closed before any adapter child execution or spawn. Windows remains usable for authoring/review and pure model/contract tests without adapter execution or spawn. The current supported-host set is empty; all actual transfers are blocked everywhere.
**Rationale**: plan-10 identifies the unresolved CreateProcess-to-Job-attachment, cancellation and launcher/supervisor-loss races. Suspended creation and quarantine alone do not ensure ownership or termination during those windows. A scope exclusion avoids claiming a safe broker without a design or evidence.
**Generic contract**: a host/adapter must already have verifiable parent-owned, killable process-tree containment before adapter code executes; terminate, wait/reap, prove no child remains and clean up before guard release. No uncontained fallback, helper-thread or multiprocessing substitute. Every admitted supported status operation returns by D through the foreground/cache boundary described below, independently of child reap; known inability to sustain that supervisor rejects platform admission. Catastrophic caller-process/OS unavailability is outside operating preconditions. Human-proposed 10s/2s and architect-proposed 500ms inline cleanup cap/250ms response reserve remain unmeasured, non-SLO defaults. No platform is claimed qualified.
**Rejected**: Windows suspended-create/Job attachment as this feature's future qualification path; an unspecified broker or outer containment as a deliverable; assuming quarantine contains a late child; ordinary multiprocessing or helper threads; inline adapters; PID exit alone as tree proof; and assuming local kill cancels remote effects. Preserve service idempotency and same-ID reconciliation.
**Deferred risk, not a deliverable**: Any Windows support requires a separate scoped design/feature and independent platform security review covering broker or outer containment, CreateProcess/Job attachment and parent-loss races. This plan promises no Windows qualification or real-host test.
Plan-10 and earlier reviews are stale after artifact edits; new independent review is required. No tests, sensors or specialist re-review ran.


### FR-003 response ownership and independent cleanup (plan-11 resolution; proposal)
**Decision**: caller-facing foreground request supervision owns the deadline, not the adapter/cleanup path. Start monotonic D before admission, reserve R for bounded response rendering/handoff and read only preloaded immutable owner/progress/evidence snapshots. All adapter operations run in validated contained children; no foreground ledger lock/I/O, fresh write, adapter call, child join/reap, cleanup, sink call or logging flush. Every admitted supported status operation returns valid current evidence before D or latest cache as unavailable/unknown with evidence age/source/revision/uncertainty and safe options by D. No current host is qualified; this is a design obligation, not measured success.
**Budget and admission**: validate positive finite wait, maximum response size, reserved bounded output channel and fixed template/nonblocking enqueue or caller return before use. Reject configuration/request before status waiting if the configured deadline or actual remaining time at admission cannot accommodate the platform-verified rendering/handoff reserve or capacity is unavailable; this is not a request claimed to meet D. Human-proposed 10s overall and 2s per-call defaults remain unmeasured; call_end=min(t+cap,D-R). R=250ms is only a proposed candidate for a verified minimum, never proof by assumption; platforms unable to prove the reserve are unsupported. If D-R is nonpositive, D-R <= t, or time before it is below the prevalidated minimum useful guard/creation/work budget, do not create a guard or spawn; immediately return bounded prebuilt cache as unavailable/unknown by D. An initially sufficient budget followed by late guard persistence instead requires no spawn and reconciliation of any unresolved guard. Proposed 500ms caps inline terminate/reap effort within remaining call budget, not a cleanup reservation or return prerequisite. Optional safe-read retries require prior confirmed cleanup and outcome reconciliation. Guard persistence/creation admission counts against D without blocking the foreground.
**Rationale**: FR-003 unconditionally bounds the user-visible wait. A contained status child may remain temporarily alive while cache return meets D; durable active/quarantine guard plus persistent killable containment prohibit same-task adapter calls, retries, ownership mutation, transfer and launch until tree death/cleanup and outcome reconciliation. Cache-only status is not a new adapter invocation. Same-ID reconciliation can query only after local cleanup; ambiguous remote effects stay blocked, prior fence never reopens. Cleanup completeness is a separate safety condition, not a reason to miss response deadline.
**Rejected alternatives**: qualifying FR-003 on successful termination/reap; waiting for a cleanup reserve to finish before responding; threads/inline host calls; fresh DB writes or locks to assemble timeout responses; blocking telemetry/log flush; mandatory retries; weakening approved spec; claiming an unsupported/unresponsive call met D because it was labeled unavailable.
**Operating boundary**: admission rejects unsupported platforms before execution, including known inability to sustain responsive foreground supervision and bounded handoff. Catastrophic caller-process/OS loss or freeze cannot provide any software response and is outside operating preconditions, not an exemption exercised by admitted supported operations or claimed deadline success. Adapter hangs, lock contention, cleanup delay and sink stalls are isolated within the design and do not weaken D. Windows remains unsupported/out of scope; supported-host set empty; Q1/Q2 exact answers and Q3 deferral unchanged. No new AWS-platform, DevSecOps or compliance sign-off: existing no-cloud, fail-closed and minimal-data contributions remain integrated.
**Review provenance**: plan-12 reported one warning about admission and non-cooperative wording. Changed plan artifacts invalidate plan-12 and earlier reviewed hashes; no current review exists and reviews remain untouched historical evidence. No independent closure, tests, sensors, reviewer, human gate or transition ran in this correction.

### Plan-12 admission clarification (proposal)
**Decision**: Reject known blocked, uncontained or non-cooperative adapters before supported status admission; unsupported Windows is rejected before call/spawn. Every admitted invocation is isolated in a contained child, never inline. Use a prebuilt immutable bounded cache or fixed empty/unknown response, fixed template and nonblocking reserved-capacity handoff; no database or logging in handoff. Every admitted supported status request meets D independently of child cleanup.
**Rationale**: preserve FR-003 and all SC-001 status classes without allowing non-cooperation or an assumed reserve to waive the deadline. Catastrophic OS freeze/process loss is outside ordinary operating preconditions.
**Rejected**: inline non-cooperative calls; asserting 250ms suffices without platform proof; accepting a deadline too short for verified handoff; spawning or creating a guard with insufficient useful budget; counting pre-admission rejection as a deadline success. This is a design obligation, not implementation, qualification or measured proof.
